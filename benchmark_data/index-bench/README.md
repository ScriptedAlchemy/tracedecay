# indexing benchmark workload

The profiled workload for `.github/workflows/hotpath-profile.yml`. It exists
so a pull request can be asked one question — *did this diff make indexing
slower?* — and get an answer that is about the diff rather than about the
runner.

Entrypoint: `crates/tracedecay-query/src/bin/tracedecay_index_bench.rs`,
built as the `tracedecay-index-bench` binary.

```text
cargo build -p tracedecay-query --bin tracedecay-index-bench \
  --no-default-features --features production,hotpath

HOTPATH_OUTPUT_FORMAT=json \
HOTPATH_OUTPUT_PATH=/tmp/index-bench.json \
HOTPATH_REPORT=functions-timing \
  target/debug/tracedecay-index-bench
```

The workload summary goes to stdout as JSON; the Hotpath report goes to
`HOTPATH_OUTPUT_PATH`. Built without the `hotpath` feature the binary runs
the identical workload, prints the identical summary, and writes no report —
every instrumentation macro compiles to nothing.

## What it measures

Four phases against the real production pipeline, no daemon involved:

| phase | entrypoint | spans it covers |
| --- | --- | --- |
| clean generation | `CodeIndexProductionOwnerV1::build_and_publish` | `code_index.extract.parser_artifact`, `code_index.build.plan_full`, chunking |
| incremental generation | the same, over an edited subset | `code_index.build.plan_increment`, retained-parse reuse |
| sealed page drain | `VerifiedSealedLexicalPageSourceV1::next_page_batch_if` | `code_index.lexical_source.batch_stage` |
| artifact ingest | `CodeLexicalArtifactBuilderV1::append_pages` | `query.artifact.append_pages`, `query.artifact.batch.*`, `query.artifact.finalization.advance_wake` |

Read the report as service demand, not wall time: extraction runs on the
rayon pool, so `code_index.extract.parser_artifact` totals CPU across
threads and will exceed the phase's elapsed time. Compare head against base
on the same span, never a span total against the process total.

## Bounds

Measured on a 16-core Linux workstation, `production,hotpath`, dev profile
(which this workspace builds optimized):

- wall: ~7.5 s (budget: 180 s)
- peak RSS: ~475 MB (budget: 4 GB)
- 260 files, 928 437 bytes admitted, 10 285 chunks, 193 sealed pages

The wall figure scales down with core count, not up: the run is ~125 s of
CPU. A 4-vCPU runner lands well inside the budget, and the workflow caps the
run with `timeout` so an overrun fails loudly instead of producing a number
nobody can trust.

## Hermeticity

The run opens no socket (verified with `strace -e trace=socket,connect,bind`:
zero calls), starts no daemon, resolves no URL, and never reads
`~/.tracedecay`. Hotpath's localhost metrics server is disabled by the binary
itself. The publication authority and projection sink are in-memory; the only
path written is a scratch directory under the system temp dir, removed before
exit. The corpus is located from `CARGO_MANIFEST_DIR`, so the working
directory does not change what is indexed.

## Determinism

Every identity, timestamp, and digest is a fixed constant or a function of the
file ordinal, and the corpus walk is ordered and `.gitignore`-blind. Two runs
admit the same bytes in the same order and produce the same
`sealed_state_digest` and `artifact_digest`; only wall time differs. The
workflow compares those digests across head and base and warns when they
disagree, because an unequal digest means the two sides indexed different
things and the timing delta is not a like-for-like comparison.

## Corpus

`corpus/` is committed and regenerated by
`scripts/generate-index-bench-corpus.py`, which is a pure function of the file
ordinal — no RNG, no clock, no environment. Rerunning it without editing it is
a no-op.

```text
python3 scripts/generate-index-bench-corpus.py
```

Current contents (`index-bench-corpus.v1`): 260 files, 928 437 bytes,
`sha256:e6d9f163e2971e2826045645f1cd71eb52b8919ea5156c169373aeeefa0ff4df`,
across Rust (90), TypeScript (70), Python (50), Go (30), and Java (20). The
mix is weighted towards the extractors that do the most structural work.

Changing the generator or the per-language counts changes the profiled
workload: bump `WORKLOAD_REVISION` in the generator and `WORKLOAD_REVISION` in
the binary in the same commit, and treat profiles from either side of that
commit as incomparable.

## Knobs

| flag | environment | default |
| --- | --- | --- |
| `--corpus DIR` | `TRACEDECAY_INDEX_BENCH_CORPUS` | `benchmark_data/index-bench/corpus` |
| `--replicas N` | `TRACEDECAY_INDEX_BENCH_REPLICAS` | `1` |

`--replicas` indexes the corpus N times under distinct logical-path prefixes.
It is for local investigation of scaling behaviour; CI runs at 1, because the
comparison wants a stable workload rather than a large one.
