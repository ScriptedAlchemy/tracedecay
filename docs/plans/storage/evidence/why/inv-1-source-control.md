## Direct Evidence Found

### Q1. Storage unit: per-root DB, global DB, worktree sharing

1. **Lineage of the per-project DB file.** The project began as a Rust port of the TypeScript `codegraph` (commit ccb6072c0b, 2026-02-26 "add original TypeScript codegraph as a submodule"). 1c0d5e2bce (2026-02-26, aovestdipaperino): "Add the db module providing a SQLite-backed persistence layer for the code graph. Includes schema with FTS5 full-text search, WAL mode pragmas for performance". Relevance: the one-DB-per-checkout unit is inherited from the original single-repo code-graph tool, not designed for multi-worktree use.
2. **Global DB origin.** d8f8b3ee83 (2026-03-24, Paperino): "Introduces ~/.tokensave/global.db that tracks all TokenSave projects and their cumulative saved tokens... (best-effort, no locking)." Relevance: the separate global DB started as a cross-project accounting counter and later grew into the registry.
3. **Repo-local to profile-sharded.** The PR #56 doc `docs/PROFILE-STORAGE-SUPPORT.md`, read at 35d3247f5d (2026-06-20, Zack Jackson): "Repo-local behavior remains the default: New projects create `<repo>/.tracedecay/` with `tracedecay.db`, `sessions.db`, branch metadata..." and "Profile storage adds profile-sharded code-project stores such as `~/.tracedecay/projects/<project_id>/`." The PR #56 body gives no motivation beyond "Add profile-sharded project storage, enrollment markers, and registry-backed resolution."
4. **The V2 design names the repository as the unit and makes worktrees views, not shards.** The 2026-07-10 plan (commit 71694e8697, ScriptedAlchemy, `2026-07-09-tracedecay-brain-rewrite.md` §7.3): "`project.db` per canonical repository/privacy domain" and "Projects, checkouts, worktrees, and monorepo subprojects are scoped views over a canonical repository shard; they are not alternative shard identities." §7.1: "`catalog.db` per profile... Owns the minimum metadata required to plan queries without opening every shard". §7.2: "`activity.db` per profile... because a session may touch zero, one, or many projects." Relevance: worktree sharing by repository identity was explicitly designed.
5. **Why multiple files rather than one.** Same plan §4 "Alternatives Considered", option A "One monolithic profile database... **Rejected because:** code graph rebuilds, transcript ingest, automation, memory, and dashboard reads would share contention and corruption blast radius. Backup, retention, privacy, and project deletion would become coarse. 'One brain' does not require one file." Option C, PostgreSQL: "Rejected as default because: it adds server operations, credentials, network failure, and an online dependency to a local developer tool." Option D, selected: "Unified logical model over federated embedded shards... Transactions remain local; outboxes and watermarks make cross-shard consistency explicit."
6. **Worktree collapse implemented.** 977d957b33 (2026-07-26, ScriptedAlchemy) "fix(storage): collapse worktree identity, refuse temp roots": "A detached linked worktree was excluded from both the repository identity marker and the registry's git_common_dir lookup, so first touch fell through to the path-hashed fallback and minted a second store for a repository that already had one... Route every project id through the repository that owns the checkout, so the fallback itself cannot mint a worktree-scoped store." Plan 16 (current text) records it as "**Local identity correction (2026-07-26).** Repository-level project/store identity now collapses a linked worktree onto its primary checkout through `repository_identity_root`... This does not merge worktree snapshot authority". AGENTS.md (current) says: "Linked worktrees share the primary checkout's project/store identity while retaining exact worktree snapshot authority."
7. **Earlier shard splits per worktree were a known defect.** cd436fc3f1 (2026-07-16): "Validated live against a four-shard split (three codex-worktree shards plus the primary), chained into one canonical store". 62603bca74 (2026-07-16): `project_id_by_identity` "swallowed repository-identity-marker conflicts as 'no identity', letting the store-layout resolver mint a fresh path-hash project id (a split shard)".
8. **Per-worktree code-index scope inside one project store.** 27b2d3cc8d (2026-09-04): "A linked branch worktree shares its project's `StoreShardIdV1` while sealing generations into its own code-index store". Plan 40 dated amendment (a0f1c05c5b, 2026-09-12) measured the cost: "Each linked worktree, including the internal `branch-worktrees` the daemon creates for branch tracking, repeats the whole stack, and no bytes are shared: 52,463 segment files across nine worktree scopes had 52,435 distinct digests because every segment embeds `authority.worktree_id`." Decision recorded: "**One content store per repository.** Segments and text artifacts live under `code-index-v1/<repository_id>/`".
9. **Per-branch DBs retired.** d04b26982e (#2731, 2026-09-29, Zack Jackson): "Every branch is a provenance scope of the one project graph store, so branch metadata... stop modelling a per-branch database." Plan 38 amendment (2026-08-07): per-branch copies retired, which "structurally removes the 'live branch stores scale as branches × full graph size' failure class".

### Q2. Synchronous Work/Workflow ports beside async store ports

1. **Original V2 store design forbade an async DB API.** 02-store-crate.md at 71694e8697 (2026-07-10), line 50: "No asynchronous database API. Application/runtime crates call synchronous repositories on owned writer/read workers." Line 509: "Repository methods are synchronous. `ShardWriter` and `ReadPool` are implementation details; callers do not receive `Connection`, `Transaction`, SQL, or path access."
2. **Sync ports blocked Tokio workers.** b82a73e8bd (2026-09-19, ScriptedAlchemy) "fix(store): release the Tokio worker while awaiting the writer": "The synchronous storage ports (`WorkAttemptStoragePort`, `WorkflowRunStoragePort`, and their siblings) reach the serialized writer actor through one-shot `async_channel` replies, and the daemon calls those ports from Tokio tasks. `recv_blocking` parked the whole worker... every failing run had two or more workers parked in `ExactSqlHandle::begin_transaction`". The fix used `block_in_place`. be67296772 (2026-10-16) later dropped that hand-off: "No Tokio worker in the daemon's acceptance suites waits on the writer any more".
3. **Current open question, framed as a choice.** Issue #4085 (2026-10-16, open): "synchronous SQLite reads parking native workers at scale: `mcp_suite` 2,683 waits... Nearly all go through `StoreRuntimeClientLease::dispatch_read`... Wrapping each caller in spawn_blocking does not scale to this count... route `dispatch_read` and the sync read paths of `ExactSqlHandle` through the async `Connection`... or make the Work/Workflow storage ports async."
4. **Runtime motivation for the native executor.** PR #3711 (merged 2026-10-13) body: "Storage settlement must outlive the request that started it. A cancelled MCP or HTTP request must not truncate an admitted write, a shard close, or a fact-store commit." And: "`recv_writer_reply` keeps the `block_in_place` guard from b82a73e8bd. Synchronous storage ports called from Tokio workers no longer starve the daemon's runtime."

### Q3. Writer actor plus reader pool, and sharding

1. **Design text.** Brain-rewrite plan at 71694e8697, §7.7: "Each SQLite shard has one bounded writer actor. It owns the write connection, serializes short transactions, and exposes typed commands rather than a shared connection mutex." Also: "Read services use bounded read-only connection pools and SQLite snapshot transactions. They never wait behind background compaction/migration without returning an explicit busy/partial state." 02-store-crate.md at the same commit, line 66: "The writer connection is owned by one thread and is never shared through a mutex." Line 517: "one thread owns the SQLite writer connection. It drains a bounded `crossbeam_channel` of 4,096 batches and at most 64 MiB of accounted payload metadata." Line 540: "Each shard has a read-only pool capped at eight connections. A query opens at most 32 shards across the profile." Line 840: "WAL remains at most 1 GiB per shard before controlled checkpoint".
2. **Why more connections do not help.** `benchmark_data/storage-concurrency/README.md` (added in #3403, removed 6a659a778a, 2026-10-12): "The runtime retains one persistent SQLite writer actor per shard file and independent WAL reader connections. Concurrent submissions to one shard are serialized and batched; distinct shard files can execute write transactions concurrently. Adding connections that write the same SQLite file does not provide overlapping write transactions."
3. **Measured shard benefit, with caveats.** MEASUREMENTS.md (same lifetime, 2026-10-09, macOS M1 Ultra, fastbuild): "At eight submitters, four shard files provided about 1.37x the median throughput and lower p50/p95 receipt latency than one file. Its p99 was higher and variable (38.7–76.3 ms versus 24.6–29.4 ms); sharding did not improve every tail metric." And: "these comparisons include batching and smaller per-file histories as well as parallel writer threads."
4. **Sessions as a separate store: reason given.** Plan §4 option A rejection (contention and corruption blast radius; see Q1 item 5). The plan also places transcripts in a profile activity shard "because a session may touch zero, one, or many projects. Project shards own scoped projections and locators, not duplicate canonical messages."

### Q4. Grafeo for the code graph

1. **First adoption was a disposable projection that ran slower.** PR #487 (merged 2026-08-03, ScriptedAlchemy): "replace the generation-local `BTreeMap` adjacency and hand-written BFS behind `CodeGraphEvidenceAdapterV1` with embedded, in-process Grafeo; keep the published code-index generation authoritative; Grafeo is a disposable read projection rebuilt once per generation". Its measurements: "about 8.8× build p50, 3.3× traversal p50, and +1.5 MiB peak RSS" versus the prior adjacency. Rollback note: "Grafeo holds only a disposable derived projection, so rollback requires no persisted-data migration."
2. **Same day: promoted to sole durable graph/vector authority.** Plan 39 at 955552d44b (2026-08-03): "**Goal:** Replace custom adjacency structures and graph-shaped SQLite storage with one embedded Grafeo runtime boundary while retaining SQLite only for genuinely relational, transactional, and content-bearing records." It lists what moves to Grafeo (code nodes and edges, Git topology, Work/workflow DAGs, LCM relations, memory relations, vectors) and what stays in SQLite ("registry, configuration... observation admission, source cursors, inbox/outbox, idempotency, effects, leases, receipts, and transactional journals; raw session/message content..."). Constraint: "Do not introduce `petgraph` or another overlapping graph/vector database." Publication protocol: "commit the canonical event and an idempotent graph outbox record in SQLite, apply the graph batch, then advance the graph watermark."
3. **Heap residency became the known cost.** Issue #836 (2026-09-03): "the shared staging Grafeo container (`proj_*/tracedecay.grafeo`, 15 GB live) accumulated the rows of 13 generations, and Grafeo's LpgStore is heap-resident, so every open replayed all of it into RAM." `docs/graph-at-rest/README.md`: "Activating a sealed generation replays every node and edge into grafeo's in-RAM `LpgStore` MVCC arenas... because `LpgStore` has no byte-addressable at-rest representation."
4. **Why a fork.** 18f3b7febd (2026-08-27): replaced the vendored copy with git-pinned `ScriptedAlchemy/grafeo` "tracedecay/0.5.42-arena-multichunk"; e3600c4971: "epoch arenas span chunks (u32 flat addressing, 4 GiB ceiling, typed InsufficientSpace/InvalidAlignment), panics converted to typed errors". d673ef8503 (2026-08-28) verdict: "the arena costs resident memory instead of saving it: +28% live VmRSS at 1M rows" and "`SectionType::LpgStore` is `mmap_able: false` and `ForceDisk` on it frees zero bytes." The disk-tier feature was retired in de789a4030 (2026-10-12, Fixes #3622).

### Q5. Turso/libSQL history and abandonment

1. **libSQL was the original engine (March to July 2026).** adf5e8143f (2026-03-23, Enzo Lombardi): "Migrate the entire database layer from rusqlite to the native libsql crate for Turso compatibility. Since libsql is async-only, all database methods and their callers are now async".
2. **libSQL caused native crashes.** 34d132e651 (2026-07-02, ScriptedAlchemy): "Root cause is upstream tursodatabase/libsql#2251: dropping a local libsql::Connection closes the sqlite3 handle twice... On Windows the use-after-free stochastically faults". Earlier, 27973c32da (2026-06-24) disabled mmap on Windows for the same crash family.
3. **V2 chose sync rusqlite.** 02-store-crate.md at 71694e8697: "V2 uses the synchronous `rusqlite` API... `rusqlite = { package = "libsql-rusqlite", version = "=0.9.30"...}`. This choice shares the SQLite C runtime already linked by V1 `libsql = "0.9.30"`, avoiding two SQLite implementations in one binary." The brain-rewrite plan says: "Remote libSQL is a future adapter, not part of the first V2 default." Cutover commits: eb93351b29 "feat(storage): complete rusqlite runtime" (2026-07-22); cfc93fa156 (2026-08-07): "The rusqlite cutover made the libSQL-era compatibility driver and its process-isolated parity helper dead weight".
4. **Formal rejection, 2026-09-30.** 81026d2ab7 / PR #2772 (Zack Jackson, 2026-09-30, plan-set-index register): "**Turso/libSQL as the local runtime is rejected (decided 2026-09-30).** ... `libsql` 0.9.30/0.10-pre is async-only with a private raw connection (no online backup, progress handler, per-connection limits, worker-thread config, custom functions, or statement cache), bundles SQLite 3.45.1 with CVE-2025-29087 unpatched, and has the open double-close bug tursodatabase/libsql#2251. `turso` 0.8.1 lacks FTS5, cross-process file sharing, and backup/limits... Revisit only when a libSQL release ships on current SQLite with #2251 fixed."
5. **The Oct 10–12 cutover attempt and its abandonment.** Issue #3402 (2026-10-10): "The user approved fresh native databases, disposal of old contents without conversion, native FTS token/ranking differences, and logical deletion without SQLite deleted-page scrubbing." PR #3409 body: "An in-place driver swap, chosen by a three-candidate arena. The writer actor, admission, receipt ledger, payload executors, exact SQL and the domain stores keep their code; only their driver calls moved". Closing comment on both #3402 and #3409 (ScriptedAlchemy, 2026-10-12T00:32Z): "Closed without merging. The native Turso cutover was abandoned on 2026-10-12: Turso 0.8.0 is not mature enough to be TraceDecay's only store (a silent wrong-result bug and about ten planner gaps surfaced during the burn-down, and the concurrent-write motivation was never realized). The repository keeps its SQLite runtime. Branches are deleted."
6. **The cutover design had already given up concurrency.** CUTOVER-DESIGN.md at 4f6a9a2160: "**WAL mode, one writer per shard, no MVCC.** `TransactionBehavior` has no `Concurrent` variant." It also deleted "The prototype's duplicate native writer, ledger... MVCC opt-in". Relevance: the writer-actor shape stayed across the engine swap, so the swap could not deliver concurrent writes.
7. **Shadow-authority rule enforced on the experiment.** PR #3403 (merged 2026-10-11) "Scope decision": "Merging it would add a second storage authority and caller branches that only test fixtures reach. That conflicts with the AGENTS.md rules against shadow authorities and unfinished features."

### Q6. Fail-closed projection drain; no first-class growth bound

1. **Ordering invariant from the design.** 02-store-crate.md at 71694e8697: a test list that includes `checkpoint_cannot_skip_sequence` and the expectation "no checkpoint advances over a gap/dead letter". Also: "Dead letters retain original sequence, error class, attempt count, next retry, and payload digest. They block 'caught up' status until resolved or explicitly quarantined." Also: "Startup recovery... quarantines corrupt shards without blocking healthy shards."
2. **Code comment in the target.** `crates/tracedecay-host-admission/src/projection_drain.rs:224-226`: "The head-of-queue failure aborts the drain (fail-closed sequence ordering); the full source chain must land in the log or the stall is undiagnosable from outside." Deterministic rejections are the exception (lines 207-214): "Breaking here would stall later healthy items until the next 60s host tick, a stall, not a cheaper path. Keep draining."
3. **Incident.** PR #3415 (merged 2026-10-10, Related to #3393): "A malformed SQLite page at the HOL projection head mapped to retryable `projection_storage_retry_scheduled`... so the drain retried the same corrupt head for ~2.5 days and nothing behind it projected." The fix makes it terminal: "SQLITE_CORRUPT / SQLITE_NOTADB become a typed `ProjectionStoreError::Corrupt` classified as blocked `projection_store_corrupt` (no 5-minute retry loop)." This fix stops the retries, but the drain still stops at the corrupt head.
4. **Retention plan sets soft budgets only.** Plan 38 (c3422239db, 2026-07-23) opening: "grounded in measured development evidence from 2026-07-23, when one owner profile reached **256 GB** and was reduced to ~75 GB purely by removing data the product should never have retained." Product contract item 7: "Owners can set soft budgets; exceeding one is a finding, never silent." Item 2: orphan stores are collected "under an owner-visible retention window."
5. **Registry GC never deletes stores.** 977d957b33 (2026-07-26): "Add plan/apply registry reaping for rows whose path no longer exists, which never deletes a file and always retains an authority whose store survives." 47fdfb0502 (2026-10-12): "registry gc retired any code_projects row whose canonical root was gone unless it owned a store instance."
6. **153 GB incident.** Issue #4099 (2026-10-16, open): "On 2026-10-16 `~/.tracedecay` measured 153 GB before the owner had it deleted. Nothing reported the growth: ... `storage.table_growth` for both `tracedecay.db` and `global.db` as 'table payload growth measurement is unavailable'". And: "`projects/` with more than 30 `proj_*` stores, one per registered root, so each agent worktree under `/fast/tmp` that ran TraceDecay carried its own full code-graph index and sessions shard". PR #4097 (open) explains why the measurement is missing: "`storage.table_growth` is `unknown` for every store. Stores above the 64 MiB synchronous cap are refused, and the Doctor preview path never seeds a baseline for small stores."
7. **WAL growth mechanism.** PR #4097 (2026-10-16, open): "SQLite restarts the log only when no reader holds a WAL read slot at the moment a write begins. The writer only ever ran `PASSIVE`, and `PASSIVE` never restarts the log. Under overlapping reads, the log therefore ratchets toward the hard limit." Live numbers: "`hard_retry_wakes: 245264`, `wal_bytes: 229797152` (soft 33554432, hard 268435456)".
8. **No-backup ruling in git.** 0708270316 / #2177 (2026-09-26, Zack Jackson): "The product kept secondary copies of project and operator data in three places. All three are removed". AGENTS.md "No secondary copies" was added in e66727df83 (2026-09-23); the commit has no body.

## Indirect / Circumstantial Evidence

- **Why async store ports exist (Q2).** The first `impl Future` store port, `TranscriptStore` in be1f535e00 (2026-07-14), was implemented in `src/global_db/transcript.rs` over `libsql::Connection`, which is async-only (diff lines show `use libsql::{Connection, params}`). Work ports (`WorkAttemptStoragePort`, 983c4e370d, 2026-08-06) came after the sync rusqlite runtime (eb93351b29, 2026-07-22). *Suggests:* the split follows the engine each port family was first written against: async libSQL for July store ports, sync rusqlite for August Work ports. *Alternative reading:* async may have been chosen for the store ports on its own merits. No commit message says either way, and both commits have empty bodies.
- **Turso motivation.** #3409's "concurrent-write motivation" comment plus the 2026-10-09 contention benchmark suggest the October attempt aimed at write concurrency. The CUTOVER-DESIGN text ("one writer per shard, no MVCC") shows the chosen design could not deliver it. No commit or PR states the motivation in full; the arena inputs (`/fast/tmp/turso-arena/...`, `judge.md`, `scope-map.md`) live outside git.
- **Turso bug inventory.** At 4f6a9a2160, `benchmark_data/storage-concurrency/turso-bugs/` lists 20 files, for example `cte-limit-parameter-drops-groups.md`, `in-after-equality-prefix-never-seeks.md`, `secondary-index-loses-to-primary-key-prefix.md` and `wal-restart-tied-to-auto-checkpoint.md`. *Suggests:* this is the "silent wrong-result bug and about ten planner gaps" in the close comment. Not read individually.
- **Fail-closed drain as head-of-line.** The design placed a dead-letter mechanism beside the no-skip rule (item Q6.1). The current drain has typed skip dispositions only for `Contract`/`SanitizationRefused`, and a corrupt head ends the drain. *Suggests:* the planned dead-letter or quarantine path for non-deterministic failures was not built, so ordering protection turns into a full stall. This is inferred from comparing the plan text with the code comment; no commit says a dead-letter queue was deliberately dropped.
- **Grafeo escalation rationale is thin.** The text found is the plan 39 goal sentence and PR #487's note that Grafeo keeps "one embedded substrate available for a future Work DAG". No commit or PR compares Grafeo with SQLite recursive CTEs or adjacency tables for durability or RSS before the escalation. PR #487's own numbers showed Grafeo slower than the replaced in-memory BFS.
- **Synchronous pragma mismatch.** The 2026-07-10 design specified `synchronous=FULL`. The 2026-10-09 benchmark ran "SQLite WAL, `synchronous=NORMAL`". 8b1a70e28c (2026-09-18) says: "The admitted telemetry connection reports SQLite FULL (2), not the writer lane's NORMAL (1)." *Suggests:* the writer lane runs NORMAL against the original design. No commit found that explains the change.

## Contradictions

1. **Worktree sharing designed and implemented vs. observed per-worktree stores.** Plan §7.3 (71694e8697), 977d957b33, plan 16 and AGENTS.md all say linked worktrees collapse onto one repository store, and `default_profile_project_id` is documented as "the only place a project id is minted, so a linked worktree cannot acquire a store of its own". Issue #4099 (2026-10-16) reports "more than 30 `proj_*` stores, one per registered root, so each agent worktree under `/fast/tmp`... carried its own full code-graph index and sessions shard". Source control does not explain the gap. Candidates I could not verify: the `/fast/tmp` checkouts may not be git linked worktrees (for example separate clones), may hit the `repository_identity_root` `None` arms ("repository shape whose primary checkout cannot be derived safely"), or may be counted per code-index scope (27b2d3cc8d, plan 40). I did not inspect the host.
2. **"No asynchronous database API" (02-store-crate.md, 2026-07-10) vs. async store ports four days later** (be1f535e00, 2026-07-14, `impl Future` in `tracedecay-store/src/transcript.rs`).
3. **Design `synchronous=FULL` vs. writer lane NORMAL** (see Indirect).
4. **libSQL rejected in July, revived in October, abandoned again.** The 2026-07-10 plan said changing the driver "requires a measured storage-driver ADR, on-disk compatibility/integrity proof, backup/restore drill, and performance parity". The 2026-09-30 register entry gave a revisit condition ("libSQL release ships on current SQLite with #2251 fixed"). The 2026-10-10 attempt targeted `turso` 0.8.0 native, not libSQL, after the register had noted "`turso` 0.8.1 lacks FTS5, cross-process file sharing, and backup/limits." The #3402 rulings accepted those losses (fresh DBs, FTS ranking change, no backups).
5. **Plan 38 says orphan stores are collected under a retention window; registry GC commits say reaping "never deletes a file".** No commit found that implements automatic deletion of orphaned project stores.
