# Reviewer C: storage redesign (docs/plans/storage/README.md, sketch.rs)

Scope: read-only. Design package, ground docs, spot checks in the worktree at `crates/`. No builds.
Paths: README = `docs/plans/storage/README.md`, sketch = `docs/plans/storage/sketch.rs`.

## Findings

### 1. [critical] Cutover step 1 does not make the step-2 fence total, and the order argument rests on that claim
**Location**: README "Cutover plan" steps 1 and 2 (l.483-506); "Synthesis decision" rejection of the judge's order (l.443-446); §3 (l.211-215).
**Finding**: The README rejects executor-first because "the executor's fence is only total once every read is a bounded job". Step 1 converts one thing: the typed `dispatch_read` and its seven callers. I confirmed seven production sites: `fact_store/runtime.rs:263`, `observation_adapter.rs:1804`, `external_source_store.rs:783/821/849/914`, `remote_query.rs:137`. After step 1 these readers are still not executor jobs:
- class (b) engine async reads (`Connection::*_async` via `spawn_blocking`: temporal, LCM, FactStore non-retained);
- sync `ExactSqlHandle` snapshots that span Begin/Query/End round trips (44 files reference `ExactSqlHandle`; 30+ are Work, Workflow, handoff, graph-publication, scope-set and remote), which go away only in step 3;
- foreign snapshot readers: `sqlite_read_snapshot::materialize/open_foreign_in` in `storage_report.rs:449-458` and `orphan_stores/collection.rs:788` (a backup-API copy of a whole store under a read mark), and `tracedecay-cli/src/commands/profile_storage.rs:199` (read-only open). `sqlite_read_snapshot` is deleted only in step 6.

So step 2's stated proof ("continuous readers keep the WAL at or under soft plus one batch") is not reachable at step 2. The classes it needs converted are scheduled for steps 3 and 6.
**Evidence**: The existing attachment already owns every in-pool reader, including exact-SQL leases and the health reader, because they share one reader pool (explanation §4, "Lanes"). The #4097 gap is foreign readers and other attachments, not unconverted in-pool readers. The README therefore buys little by putting step 1 first for the fence. A fenced TRUNCATE can be done on the existing attachment with the existing pool's visibility, and it closes the acute 229 MB WAL.
**Suggestion**: Reorder by independence and incident severity, not by the fence argument. Per-stream dead letters, TEMP-table removal and typed fault classification (the 6-day freeze), persisted usage and retention (the 153 GB), and the fence on the current attachment need neither the pool rewrite nor the Grafeo-to-SQLite move. As written, the freeze fix is step 5 and the growth fix is step 7, behind steps 1-4. Land those first. State honestly that the fence is "total over executor readers plus a typed foreign-reader degrade path" until step 6 removes the foreign readers.

### 2. [critical] Evidence/derived split breaks crash consistency under `synchronous=NORMAL`: the derived cursor can lead the evidence it points into
**Location**: README §3 (l.205-208), §2a "No transaction spans two files" (l.192-197); sketch `ClassPolicy` Evidence and Derived (l.353-372); `projection` module doc (l.980-983).
**Finding**: Evidence and derived are separate NORMAL files. Each commits to its own WAL, and neither is fsynced at commit. After an OS crash or power loss the two files can recover to different points. Derived can keep `projected_through(stream)=N` while evidence recovers to a point before N. The recovery rollback is internally consistent per file: evidence's cursor, rows and `AUTOINCREMENT` counter all roll back together. Capture then re-reads host JSONL and re-issues the lost sequence numbers, possibly in a different order or interleaving across sources. Derived believes those sequences are already projected, so the new rows are skipped. Or it holds projections of old rows under reused sequence numbers.
**Evidence**: Today, `project_observation` reads the observation row, writes messages, consumes the queue item and writes the checkpoint in one `sessions.db` transaction (`observation_projection/rebuild.rs`, `project_observation`). The split replaces one atomic unit with a producer commit, a separate consumer commit and a cursor that references the producer's identity space. README claims the consumer-keeps-its-cursor rule is sufficient. It is sufficient for process crashes only. FULL vs NORMAL per class makes the mismatch likely, because the producer is the weaker file.
**Suggestion**: Give evidence an immutable per-incarnation epoch id, or a monotone `max_durable_seq` that is advanced only after a checkpoint or fsync. Derived records the `(epoch, seq)` it consumed and refuses or rewinds on a mismatch at open. Alternatively, make the projector read only below an evidence watermark that has been synced (PRAGMA wal_checkpoint plus fsync of evidence before advancing the derived cursor).

### 3. [critical] LCM summaries are placed in evidence, but the summary DAG references derived-local ids and tables
**Location**: README §2a "Two merges, and why" (l.188-190); table rows for evidence and derived (l.163-164); sketch `SessionStore::record_summary` (l.540-544).
**Finding**: README says summaries join evidence "because summaries can be LLM-generated and are not rebuildable" and that raw eviction depends on them. The summary machinery references derived-side identity:
- `lcm_summary_convergence_queue`, `_dirty_raw` and `_invalidation_work` FK to `sessions(provider, session_id)` and use `newest_raw_store_id` / `raw_store_id` (`tracedecay-lcm/src/summary_convergence.rs:17-60`).
- `lcm_raw_messages` and `lcm_raw_predecessor_ranges` carry the `store_id` autoincrement and FK to `sessions` (`tracedecay-lcm/src/schema.rs:346, 373, 445`).
- Summary sources are `session_summary_sources` in the temporal schema.
All of that ends up in derived (sessions, raw index) or has to be split across both files. If summary nodes sit in evidence and their sources use derived `store_id`, a derived drop-and-rebuild (a routine path: schema mismatch, over-budget step 7, `Rebuild` corruption policy) re-numbers store ids and dangles every summary source. If the convergence queue sits in derived with its FK, summary generation state is lost on rebuild and LLM summaries are regenerated, which is the cost the placement was meant to avoid.
**Evidence**: The README says only "contentless FTS5, rowid = evidence sequence" for the index. It does not say that `store_id`, summary sources and the convergence queue are re-keyed to evidence sequence. Open Questions never mention the summary DAG.
**Suggestion**: Re-key summary sources and the convergence queue to evidence sequence (or canonical observation id) before the split, and say so in step 5. Move the convergence queue to whichever file owns the cursor. Add a rebuild test that drops derived after summaries exist and asserts `lcm_expand` still resolves.

### 4. [critical] `WorkJournal::transition` cannot express today's atomic Work invariants, and the sketched order loses replays
**Location**: sketch `JournalAggregate` and `transition` (l.409-466); README §4 (l.248-253), §8 (l.361-363).
**Finding**:
1. `decide: FnOnce(Option<&A>)` sees one aggregate. `WorkAttemptStoragePort::insert_bounded` (`tracedecay-contracts/src/work_attempt.rs`, doc ~l.118-127) is a capacity check across the project, repository, task and route plus the insert, "one storage transaction so two concurrent admissions cannot overbook". `next_fence_epoch` mints a per-authority monotone counter. `update` CASes the fence and writes an evidence row in the same transaction. Workflow definition activation retires the previously active definition. A single-key pure function cannot read counts or sibling rows, so these either need the closure to receive a read view of the transaction (a larger surface than the 3-method claim admits) or they leave the journal as bespoke methods. The 77 to 3 reduction will be 3 plus the unexpressed cases.
2. `list<A>(filter: A::Filter, ..)` moves the 77 verbs into `Filter` enum variants. The count falls; the surface does not.
3. Order bug in the sketch pseudocode (l.458-464): `decide(current)` runs first, then `idempotent_replay(decision.operation_id)`. A replayed command whose aggregate has already moved on (cancel of an already-cancelled attempt, a retried approval) makes `decide` return an error or a different decision, so the replay returns that instead of the recorded outcome. The operation id must be an input to `transition`, and the ledger check must precede `decide`.
4. `type Outcome: Send + 'static` has no serialization bound, but the ledger "returns the original Outcome" from a persisted row.
5. Retry contradiction: `WriteJob`/`ReadJob` are `Box<dyn FnOnce>` (l.825-826) and `transition` takes `FnOnce`. The §5 recovery for #4094 ("drop every connection and retry the job once on a fresh connection") needs to run the closure twice. A consumed `FnOnce` cannot be retried. The central containment mechanism for the 6-day freeze is not implementable with the declared types.
6. Ledger placement: "idempotency 7 d" is listed under `journal.db`. `MemoryStore::commit` and `SessionStore` writes live in other files and need a ledger row in the same transaction as the effect. A cross-file ledger is not atomic. Each writing file needs its own ledger and pruning rule.
**Evidence**: Cited contract text and sketch lines above.
**Suggestion**: `transition(op_id, key, decide: Fn(&JournalTx, Option<&A>) -> Decision)` where `JournalTx` is a read-only view of the open write transaction; make closures `Fn` (re-runnable, pure) or make the retry explicit in the lane. Require `Outcome: Serialize + DeserializeOwned`. Name the per-file ledger.

### 5. [critical] Root-commit identity strands durable memory on every re-key, and the "cache" marker also holds an authoritative override
**Location**: README §2 (l.133-150); sketch `identity` module (l.221-259); README §9 `init` (l.369-372).
**Finding**:
- Re-key without migration. The anchor changes for shallow-to-unshallow (`Remote` to `RootCommit`), `Path` to `RootCommit` at first commit, history rewrite (`filter-repo`, `rebase --root`, BFG), a fetch that brings in a second root, or marker loss. The sketch says "Re-keyed when unshallowed" and "the path-keyed set then has no live checkout and is collected". Nothing moves `memory.db`. Facts and holographic banks written before the first commit or while shallow stay in a store that `RepositoryButMemory` keeps on disk but nothing resolves. The user sees memory vanish.
- Anchor is HEAD-dependent. README says "smallest parentless commit reachable from HEAD". The sketch (l.243-244, 253) says "gix first-parent walk". These are different functions. A first-parent walk finds only the first-parent root. Reachable-from-HEAD changes with the branch, so two linked worktrees on branches that merged unrelated history (subtree adds, `--allow-unrelated-histories`) compute different smallest roots. The marker caches whichever resolved first, so the id depends on process order.
- Collisions. Roots with a fixed author date and tree (reproducible-build fixtures, `git commit --allow-empty` bootstrap scripts, templates scaffolded with identical first commits) have identical root commits. Unrelated repositories then share a store silently, memory included. Nothing detects it.
- Monorepo subdirectory projects regress. `repository_identity_root` (`tracedecay-runtime-core/src/worktree.rs`) deliberately returns `None` for a non-root directory: "a package directory inside a monorepo is its own project"; "Without this check a subdirectory indexed as its own project would be absorbed into the enclosing repository's store". The sketch's `Checkout::discover` "Walks up to the worktree root". That removes per-package projects with no replacement. `WorktreeId` hashes the worktree root, so per-package code scopes cannot be represented either.
- The marker is documented as "a cache of the anchor computation, not an authority", yet `Marker.explicit` (sketch l.245-249) and `project link --as/--split` persist an authoritative override in it. A marker lives in `<git_common_dir>`, so another clone does not see a `--split` and re-derives its own id; deleting the marker silently drops an override. The catalog `aliases` rows are mentioned but not given this role.
- `repository()` does a catalog upsert on every call (sketch l.97-100: "one small write"), on a FULL (fsync) class, from every hook and request, plus a gix walk on an executor thread when the marker is cold. That is a hot-path durable write and an O(history) walk on a lane shared with config and usage.
**Evidence**: README l.136-143, l.246; sketch l.233-258, l.97-100; `worktree.rs` doc on `repository_identity_root`.
**Suggestion**: Make the catalog the authority for overrides and for the `anchor -> repo_id` mapping, and the marker only a cache. Define re-key as an explicit migration that moves or merges `memory.db` and writes an alias row, never a collect. Fix one anchor definition (the full set of parentless commits reachable from all refs, hashed together, or the smallest over `--all`). Decide subdirectory projects explicitly. Debounce `last_seen`.

### 6. [critical] Growth is bounded by budget enforcement that cannot reach the biggest classes, not by construction
**Location**: README §6 (l.282-318), cutover steps 4, 7; sketch `retention::plan` (l.1077-1093), `Eviction` (l.1052-1065).
**Finding**: The incident was 153 GB unmeasured. The design measures everything, but the planner can only shrink evidence, derived and terminal journal rows. Several unbounded paths are left:
- Code dirs. `worktrees/` generations are "active plus 2, 7 d" per worktree. The ground doc records generation files as "routinely ~1 GiB each". The host has 14 clones plus 32 linked worktrees (46 worktrees). That is up to 46 × 3 × ~1 GiB ≈ 138 GiB of sealed generations alone, over the 64 GiB profile budget, and the planner has no eviction variant for a live worktree's generations. Planner step 6 ("profile over budget → step 5 on LRU repositories") exhausts evidence and still reports over budget.
- Journal reset or schema change orphans sealed files. `Journal` policy is `Reset` on schema mismatch and `ResetWithFinding` on corruption. Graph heads live in the journal. Reset drops every head. The sealed generations under `worktrees/<id>/` are then referenced by nothing, and no `Eviction` variant sweeps unreferenced sealed generations (only `code/segments` has an "unreferenced sweep"). That is the same shape as today's `tracedecay.graph-replay/` and `.staging-*` leaks.
- Reactive enforcement. `maintain` runs every 10 minutes. An initial ingest of years of transcripts, or a re-ingest after an evidence reset, can write far past the 8 GiB budget between ticks. The only hard stop is "WAL past 512 MiB returns Busy". There is no file-size cap on a write.
- The 1.5× derived rule can loop. Planner step 7: "derived over 1.5× evidence → DerivedTrim; if still over → DerivedDropAndRebuild". Evidence stores deflated bodies; derived holds the FTS5 index, temporal occurrences (and its own FTS), assertions, LCM and topology. The ground doc says one line is stored up to four times. If derived's natural size exceeds 1.5× compressed evidence, which is plausible and unmeasured, each tick drops and rebuilds derived (hours: the 2026-07-23 stall was a 6 h session-temporal rebuild; the CI journey measures ~600 s page pass). The planner has no hysteresis and no "rebuilt size is the new baseline" rule.
- Sequence-prefix eviction vs a time window. `Eviction::Evidence{ before_seq }` and "oldest first" are sequence-based, but retention is "180 d window". Sequence is ingest order, not time order. An archive backfill ingests old transcripts with high sequences, so a time window is a scattered delete that `before_seq` cannot express, and old data survives the window or new data is evicted first.
- Seal-time memory. README fixes steady-state heap ("heap after open is independent of generation size"). The scratch container for a seal still replays and builds a generation-size mutable Grafeo container. The CI journey note records seal RSS 13.7 GB, and `scratch/` can hold an 8.6 GB container. Seal concurrency is unbounded.
- Open question 2 ("Do dependency-bearing graph generations need staging rows?") decides whether growth source 3 is closed. If yes, the fallback is a long-lived per-worktree scratch container, which is the object that caused the 20+ GB heap and the unbounded WAL.
**Evidence**: explanation inventory rows 21-25 (generation sizes, replay pool); README l.154-168, l.286-298, l.560-562; sketch l.1091-1092.
**Suggestion**: Add `Eviction::{Worktree LRU, OrphanedGeneration}` and a worktree-count or per-repository code budget. Add a write-time hard file-size ceiling per class that returns `Busy`/`Refused`. Make step 7's derived rule converge (measure derived-to-evidence ratio and use it as a floor; never rebuild twice in a window). Time-window eviction should key on observation time with a secondary index, or window by sequence only if capture order is made time-monotone per source. Bound concurrent seals.

### 7. [warning] The corruption confirm ladder is O(file) on a deadline-bound pool thread, and its terminal action destroys non-rebuildable rows
**Location**: README §5 table rows "Poison input" and "Corrupt file" (l.273-275); sketch `fault` (l.930-971), `OnCorruptFile::ReingestAfterConfirm` (l.286-287).
**Finding**:
- `PRAGMA quick_check(1)` returns early only on the first error. A healthy file requires a full B-tree scan, so "a pass means poison input" requires scanning the whole 8 GiB evidence file on the lane's thread. That exceeds the 5 s evidence read deadline, so it would be `TimedOut`/interrupted. The ladder's outcome for that case is not defined. It also occupies one of six pool threads for minutes per suspect fault, during a failure.
- The #4094 trigger was "a run of interrupted statements". The design interrupts statements as normal operation (read deadlines, fence). The root cause is not identified (#4094 is open). "Schema code creates no TEMP tables" is a convention with no enforcement. Production code still has `CREATE TEMP TABLE` in `observation_projection/state.rs` (2) and `rebuild.rs` (4), plus `tracedecay-query/.../clones.rs`. The connection-recycle-and-retry bound is sound; the claim that #4094 "has no state to live in" is not established. The TEMP cache existed for performance: `state.rs` documents that rebuilding the output-state aggregate "scans the whole ownership table once per queued observation" without it. The design replaces it with "Rust structures or ordinary derived tables" and also closes the writer connection after 60 s idle and on every suspect fault, so that scan repeats at each reopen.
- On a confirmed file fault evidence is unlinked and re-ingested "from host files". Evidence retention (180 d) exceeds host transcript retention, so rotated-away history is lost, and so are LLM-made summaries the design just justified keeping in evidence (finding 3). One bad page triggers this automatically with no operator step.
**Evidence**: README l.273-275, l.458-459; `state.rs` ~l.577-641; sketch l.286-287.
**Suggestion**: Bound the ladder by size (run `quick_check` only on derived and small files; for evidence use a chunked integrity probe on a background-class job with its own deadline). Make the unlink-and-reingest path require a loss receipt that names summaries and rotated history, and exclude summaries from the unlink (separate small file, or keep them in the memory class if they are non-rebuildable). Add a lint or checked schema gate for TEMP DDL, and replace the performance cache with an incrementally maintained ordinary table in the same transaction as provenance writes.

### 8. [warning] Fence latency and semantics are underspecified; "the daemon is the only process that opens these files" is false today
**Location**: README §3 (l.209-227); sketch `Fence`, `checkpoint_decision` (l.803-896), `block_on` (l.898-910).
**Finding**:
- A fence "lasts at most one read deadline plus the TRUNCATE", but all new reads queue for that long. For foreground classes the deadline is 2 s. If a read's deadline starts at submit, which the README does not say, reads that arrive in the first part of a fence expire while queued, turning every WAL-soft crossing into a burst of `TimedOut`. At a 32 MiB soft limit and multi-MiB batches, evidence reads stall up to 5 s every few dozen batches during active ingest.
- `InterruptHandle::interrupt()` is connection-wide and raced: an interrupt issued after the intended statement finished can hit the next job on that connection. The sketch has no job-generation guard.
- The fence depends on the daemon being the only opener, and on no read transaction leaking from a job. Neither is enforced by type. `rusqlite` statements can retain a read mark if a cached statement is returned unreset.
- Offline openers exist: `profile_storage.rs:199` (read-only open), the foreign snapshot paths in finding 1, and the "CLI, doctor and hook processes can build their own registry" note in the ground doc. The cutover lists no step that routes them through the daemon. `Executor::block_on` is "for offline CLI threads that own no runtime", which only makes sense if offline CLI constructs a `Storage`; but `Storage::open` "takes daemon authority" and the sketch doc says "Offline CLI commands only unlink files under the lifecycle lease". The two statements conflict, and the sync door survives.
**Evidence**: README l.216-227, l.257-258; sketch l.898-910; `profile_storage.rs:199-201`.
**Suggestion**: Specify the deadline clock (from lane admission excluding fence wait, or fence wait counted separately). Add a per-job generation to interrupts. Decide whether any CLI opens storage; if none, delete `block_on`. If some do, say how they coexist with the lease. Make the pool's `ReadTx` the only way to touch a connection (no `prepare_cached` outside it).

### 9. [warning] Dead-letter requeue and per-stream cursors re-project whole streams and fight the global frontier
**Location**: sketch `requeue_on_new_projector` (l.1024-1029); README §5 (l.271), open question 4 (l.565); `rebuild.rs` frontier code (l.393-566).
**Finding**:
- Requeue "moves the stream cursor back to the earliest such row of that stream". A dead letter at sequence 100 in a stream projected through 100,000 re-projects 99,900 rows on every requeue event. Requeue fires on a projector version change "and once per daemon incarnation". A permanent poison row therefore costs a stream re-projection per restart, forever.
- `Eviction::Evidence{ before_seq }` is a global bound, but the cursors are per stream. A stream parked on a transient fault (up to 1 h) or dead-lettered behind the bound has rows evicted before they were projected or dispositioned, with no record. Order eviction on `min(projected_through)` or record a "gap: evicted" disposition.
- The existing rebuild is set-oriented SQL over `observations`, staged tables and `lcm_raw_messages` (`rebuild.rs` `json_extract_neq_predicates`, `MERGED_SESSION_JSON_COLUMN`, a global `frontier_sequence`), all in one file. The split forbids ATTACH ("Nothing is ATTACHed"), so the rebuild becomes row transfer between lanes, and the frontier is per stream. README acknowledges the frontier in one question; it is the largest rewrite in step 5.
- Eviction cascade crash window: evidence evicts, then derived cascades "in the next derived job". A crash between leaves derived rows and FTS postings for evicted sequences, and `search` hydrates bodies from evidence. A derived-side `evicted_through` watermark and a tolerant hydrate are needed. Also, contentless FTS5 needs `contentless_delete=1` (SQLite 3.43+) to support the cascade delete and cannot produce `snippet()`/`highlight()`; I did not verify the bundled SQLite version.
**Evidence**: Cited code and sketch lines.
**Suggestion**: Requeue should re-project only the dead row (and mark its dependents), not rewind the cursor. Gate eviction on the minimum cursor or write an explicit eviction gap.

### 10. [warning] Beta upgrade path and memory importer have unresolved cases
**Location**: README §7 (l.331-339), cutover "Upgrade path" (l.534-536).
**Finding**:
- `wipe --stale` resets `ProjectSessions`. Work, Workflow definitions and run history, handoff grants, git-index and native-integration journals live there (explanation §Gotchas). The journal class is labelled "authoritative", FULL, yet its schema policy is `Reset` (sketch l.339-340) and the beta upgrade wipes it. `workflow_definition_source_journal`/`_transition_journal` (`workflow/schema.rs:400-421`) hold user-authored definitions. Nothing says which journal aggregates are durable user state and which are transient. Each future journal schema bump repeats the loss.
- The importer runs from `init` per project and "copies memory_v2_* rows and configuration revisions". It needs the old `proj_*` → new `repo_*` mapping, which requires the checkout to still exist on disk to compute a root commit. The orphans the ground doc describes (`proj_*` for deleted worktrees) cannot be mapped. 14 clones collapse into one repository, so the importer must merge fact ids, lineage and `as_of` ordering, supersede chains and holographic banks. The README describes a copy.
- Old `projects/<id>/` directories: step 6 deletes `projects/<id>/` resolution, and the unregistered-directory sweep covers `repos/`. Every old dir not touched by `init` (profile `global.db` 2.58 GB, `user-sessions.db` 45.7 GB, `user-memory.db`, project dirs) stays on disk and outside the new budget. That repeats the 153 GB shape.
- Importer crash safety and ordering: partial import then old-dir deletion, daemon starting and committing facts at the new id before `init`, and import into a non-empty `memory.db` are not specified. "Deleted two releases later" is a calendar-based shim; AGENTS.md says complete cutovers in one slice and delete compatibility code.
**Evidence**: README l.331-339; explanation inventory rows 1-3, 17-18, 31.
**Suggestion**: Classify journal aggregates (durable vs transient) and give durable ones `Migrate`. Make the importer a daemon-startup step keyed by the old project manifest (`store_manifest.json` has identity), idempotent via a completion marker, with an explicit merge policy. Have step 6 delete or adopt every legacy `projects/` directory.

### 11. [warning] Cutover has no step that delivers the new public surface or deletes the kernel
**Location**: README §8 (l.341-365) vs cutover (l.483-536).
**Finding**: The census lists what is deleted: 19 store traits (143 methods), the kernel ports (`PhysicalRuntimeAttachment`, resolver, publisher, `VerifiedGraphRuntimePortV1`, leases, probes with 13 implementations), the closed serde protocol (`RuntimeReadOperationV1`, 15-variant `RepositoryWritePayloadV1`) and the SQL/WAL/string-matching exports from `tracedecay-store`. No step introduces the `tracedecay-storage` crate, `MemoryStore`, `SessionStore` or `Repository`, migrates FactStore/ObservationStore/Temporal/LCM callers, or deletes those. Step 1 keeps the typed protocol; step 2 swaps threads underneath the old registry and leases; step 5 claims a per-stream cursor API with no surface it lands on. The compatibility-free convergence AGENTS.md requires is therefore unverified. Other sequencing costs:
- Step 3's `WorkJournal` runs over `sessions.db` until step 5 relocates its tables, so Work state changes shape twice.
- Step 4 puts the memory graph and session-relation graphs into SQLite tables in whatever file exists (`user-memory.db`, `sessions.db`), then step 6 moves memory and step 5 moves session relations again. Is the memory graph authoritative? The ground doc marks the Grafeo memory graph as `Deriv`, yet README places it in `memory.db`, the never-evicted FULL class, inflating the class that cannot be shrunk and widening the salvage-and-swap surface.
- Step 5 bundles seven changes (split, journal move, per-stream cursors, dead letters, external-source fold, blob inlining, deletions) with two proofs.
**Suggestion**: Add a step that creates the crate and migrates one port family at a time, with each family's old trait deleted in the same wave. Split step 5 as in finding 1. Decide whether the memory graph is derived (rebuild from `memory_v2_*`, keep out of `memory.db`).

### 13. [nit] Parallel authorities and typed-failure gaps in the sketch
**Location**: sketch `RepositoryId`/`WorktreeId` (l.191-196), `Refusal::InvalidInput(String)` (l.661), `ClassName` vs `StorageClass`, `Executor::start` signature.
**Finding**:
- `tracedecay-domain` already defines `RepositoryId` and `WorktreeId` (used by `WorkAttemptV1`/authority scope, `work_product_event.rs`, `research/anchor.rs`, e.g. `has_open_attempts_in_exact_scope(project_id, repository_id, worktree_id)`). The sketch defines new same-named types with different meaning (`repo_<hash>`). The Work authority also carries `ProjectId`. The README does not say how `project_id` maps.
